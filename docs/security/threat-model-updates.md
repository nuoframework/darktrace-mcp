# Threat model addendum: the update lifecycle (`update`, `--rollback`, update modes)

Scope: the installer commands added for release 1.1.3 (`darktrace-mcp update`, `update --check`, `update --rollback`, the `setup` update-mode question and the `test` / `doctor --online` update line). They extend the installer boundary described in [threat-model.md](threat-model.md) (B6, release artifact and dependency integrity) with a new flow: code chosen at update time, from the public npm registry, written into client entries on the operator's machine. The MCP server runtime (`src/index.ts`, `src/server/**`, `src/client/**`, `src/policy/**`) gained no registry access and no update check; everything below lives in `src/cli/` and runs only when the operator invokes a command. Implementation: `src/cli/registry.ts`, `src/cli/update.ts`; tests: `test/cli/update.test.ts`.

Assets: the bytes every client starts (fixed copies, image IDs), the client configuration files, `setup.json`, the token files (read by the new copy's `--check-config`, never printed or copied), and the operator's trust in "what is installed is what was published".

Actors: a compromised or impersonated registry; an attacker able to publish under the package name; a network adversary between the operator and npmjs.org, ghcr.io or api.github.com; a local same-user process racing the installer; an operator typing the wrong flag; and, in the always-latest mode, the registry at every client start.

## Register

| ID | STRIDE / severity | Threat and boundary | Control (where) | Residual risk | Tests |
|---|---|---|---|---|---|
| TM-U-01 | T,S / High | **Registry compromise or malicious publication.** A tampered registry document, tarball or a version published by an attacker reaches the fixed copy and then every client (B6). | Registry fixed by flags on every npm call (`--registry`, scoped `--@nuoframework:registry`), so `.npmrc`, `npm_config_registry` or a scoped override cannot redirect (`registry.ts`). npm verifies each tarball against the registry's `dist.integrity`. `npm audit signatures` must succeed with at least one verified registry signature; when the target's registry record announces provenance, at least one verified attestation is required, otherwise the update stops before any copy exists (`verifySignatures`). The downloaded tree is only ever written to a fresh private temporary directory and removed afterwards. The new copy runs `--check-config` and the appliance is probed before any entry changes. | A fully compromised npmjs.org (signing keys and attestation pipeline) or a valid provenance from a different repository: npm does not pin the certificate identity to this repository's workflow. Operators who need that bind run `gh attestation verify` on the release asset ([releases.md](../releases.md#verifying-release-signatures-and-provenance)). The ghcr image is not signature-verified by `update`; its digest is printed for comparison with the release notes. | `update --yes downloads, verifies…`, `a failed appliance probe, signature check or --check-config…`, `registry answers are validated and the registry is never configurable` |
| TM-U-02 | T / Medium | **Downgrade.** An attacker-controlled "latest", a stale mirror or a typo moves clients to an older version with fixed vulnerabilities (B6). | Versions are parsed strictly (`isPackageVersion`) and compared semantically (`compareVersions`, pre-releases older than releases). A target older than `installedVersion` is refused with exit 1 before any download unless `--allow-downgrade` is given explicitly; `--rollback` cannot take a version. `update --check` reports "up to date" when the registry offers something older. When no version is recorded (Docker pinned by digest or ID) the command says so instead of comparing silently. | The operator can still downgrade on purpose; `--rollback` returns to the recorded previous version by design (TM-U-04). The `latest` dist-tag itself is registry-controlled. | `update refuses a downgrade unless --allow-downgrade…`, `compareVersions orders releases and pre-releases` |
| TM-U-03 | T,D / Medium | **Partial write or interrupted update.** A crash, a full disk or a kill between steps leaves a half-written client file, a mixed set of entries or a `setup.json` that points at nothing. | Ordering: download, verify, copy, check-config, probe, and only then rewrite entries and state; any failure before the rewrite changes nothing (`runUpdate`). Each client file is backed up and replaced by `atomicWrite` (temp file in the same directory, fsync, rename; symbolic links refused). The fixed copy is assembled in a sibling temporary directory and renamed into place; an incomplete copy is detected and rejected (`installFixedCopy`). `setup.json` is written atomically after the entries and only when every client was rewritten; otherwise it keeps the previous version so the next `update` repairs the rest instead of reporting "up to date". For CLI-managed clients (Claude Code, Codex) a failed `add` after the `remove` is followed by re-registering the previous entry. A directory already present under the target version is replaced by the verified download, never reused. The temporary download directory is removed on every exit path. | A failure between the rewrite of client A and client B leaves them on different versions until the operator reruns `update` (which moves the rest and reports the others unchanged). Backups are never deleted automatically. | `a failed appliance probe, signature check or --check-config leaves every client entry and the state untouched`, `a client that cannot be rewritten keeps setup.json on the previous version…`, `when claude mcp add fails after the remove, the previous entry is registered again`, `a directory already present for the target version is replaced…`, `update --dry-run prints the plan and downloads nothing` |
| TM-U-04 | S,T / Low | **Rollback abuse.** `--rollback` used to reinstate a vulnerable version, or a crafted `setup.json` pointing `previousEntryPath` at attacker-controlled code. | Rollback is explicit, asks once (or `--yes`), and only returns to the version `update` recorded. `previousEntryPath` must be absolute, must describe this package (`describeEntry`: name and exact version read from its `package.json`) and must match `previousVersion`; `previousImage` must be an image ID that the Docker daemon still has (recorded even when the setup pinned by digest and no release version is known). The previous copy runs `--check-config` offline before the entries change. `setup.json` is 0600 in a 0700 directory owned by the operator. | A same-user attacker who can edit `setup.json` can already edit the client files directly; this control does not defend against that principal. Rolling back reinstates whatever the previous release's known limitations were; the summary names the version. | `update --rollback returns to the previous copy and swaps the pointers; a missing copy is refused`, `docker runtime: update pulls the release tag… keeps the old one for rollback and uninstall`, `docker setups pinned by digest (unknown version) warn…` |
| TM-U-05 | T,S,D / High (opt-in) | **Always-latest mode.** With `updateMode: npx-latest` every client start runs `npx -y @nuoframework/darktrace-mcp@latest`: the registry decides the code at each start, with none of the checks above, and a registry outage stops the client. | Off by default and never chosen silently: `setup` asks the question with the trade-off spelled out (interactive) or requires `--update-mode npx-latest` (non-interactive); the flag is refused for the Docker runtime. The launcher keeps the token-file environment (no token values), uses the absolute `npx` path when found, and the mode is recorded in `setup.json` for the node runtime only (a later Docker setup never inherits it) so `config` and `update` describe it honestly (`update` has nothing to move; no silent pinning). `setup --update-mode pinned` reverts to a verified fixed copy. Documentation lists this mode as the unverified path ([update.md](../update.md#update-modes)). | The risk is accepted by the operator who chooses it: no signature, provenance or appliance check before new code runs, and `npm` itself (with its own configuration) performs the fetch. The installer's documentation scan (MR-03.DISTRIBUTION) still forbids unpinned launchers in examples, so this mode appears in prose only. | `setup --update-mode npx-latest writes npx launchers…`, `interactive setup asks for the update mode after the profile…`, `a saved npx-latest mode never leaks into a docker setup` |
| TM-U-06 | T,I / Low | **Untrusted release notes.** `update --check` prints the GitHub release body on the terminal; a tampered body could carry terminal escape sequences or misleading instructions. | Fetched only over HTTPS from `api.github.com` with a 10 s timeout, no redirects and a 512 KiB cap (`fetchTextBounded`); ANSI escapes and C0/C1 control characters are stripped and the text is bounded to 60 lines / 6000 characters before printing (`releaseNotes`). The notes never influence what `update` installs: the version comes from the registry query and the bytes from npm. | Misleading prose in a compromised release body is still shown to a human; the command recommended by `update --check` is generated locally, not taken from the notes. | `update --check compares versions, prints the release notes…` |
| TM-U-07 | T,E / Medium | **Local filesystem races.** A same-user process replaces the fixed-copy parent, the temporary directory or a client file with a symbolic link during the update. | Same rules as `setup`: `fixedCopyDir` accepts exact versions only (no path components), parents that are symbolic links are refused, copies skip symbolic links and `.bin` shims, client files that are symbolic links are reported and not modified, writes use `O_EXCL` temporary files. The download directory comes from `mkdtemp` (0700). | Protection is against mistakes and ordinary tampering, not against a same-user attacker, who already owns the client files and token files (see TM-02 residuals). | existing `npx-install.test.ts` and `uninstall.test.ts` symlink cases, `older setups without an entry path…` |
| TM-U-08 | I / Low | **Update check as an information leak.** `test` and `doctor --online` contact registry.npmjs.org and reveal that this host uses the package. | The check runs only after a successful appliance probe in those two commands, never at server start, never from the MCP process, and is skipped silently when npm or the registry is unavailable. `update --check` contacts api.github.com in addition and only when the operator runs it. No appliance address, token or client name is sent anywhere: the query is `npm view` of the package name. | The registry and GitHub see an npm user-agent and this CLI's `darktrace-mcp-cli/<version>` user-agent respectively. Operators on isolated networks run `test` as before; the extra line simply never appears. | `test and doctor --online print one "Update available" line only when a newer version is published` |
| TM-U-09 | I / Medium | **Token exposure during verification.** The new copy's `--check-config` receives the token-file paths in its environment; a malicious new copy could read the tokens. | By the time `--check-config` runs, the copy has passed the registry signature and provenance checks (TM-U-01); it is the same code the clients will start a minute later. The check runs with the same environment `test` uses (file paths, never values), no network, a 60 s timeout, and the only thing parsed from it is `{"ok":true}`. The installer never prints or copies token values; `update` refuses the Windows inline mode outright because it would need to read values back. | A malicious version that passed the supply-chain checks can read the token files, as any update mechanism that runs new code must accept; the mitigation is TM-U-01 and the operator's ability to pin with `--version` and verify release assets by hand. | `update refuses to proceed for setups it cannot move…` (Windows inline), `a failed appliance probe, signature check or --check-config…` (no probe after a failed check) |

## Decisions

- `update` never runs lifecycle scripts, never follows a configurable registry, never writes a transient `npx` path into a pinned entry, and never prints a token.
- The appliance probe before the rewrite is deliberate even though the previous version already passed it: it catches rotated tokens, changed URLs and expired certificates before a working client is turned into a broken one, at the cost of one signed request.
- The previous copy and image are kept, not deleted, so that `--rollback` works offline; `uninstall` is the single command that removes them, together with everything else the installer created.
- The always-latest mode exists because some operators asked for zero-maintenance clients; it is documented as the unverified path and is never the default.
