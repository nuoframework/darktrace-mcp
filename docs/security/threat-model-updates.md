# Threat model addendum: the update lifecycle (`update`, `--rollback`, update modes)

Scope: the installer commands added for release 1.1.3 (`darktrace-mcp update`, `update --check`, `update --rollback`, the `setup` update-mode question and the `test` / `doctor --online` update line). They extend the installer boundary described in [threat-model.md](threat-model.md) (B6, release artifact and dependency integrity) with a new flow: code chosen at update time, from the public npm registry, written into client entries on the operator's machine. The MCP server runtime (`src/index.ts`, `src/server/**`, `src/client/**`, `src/policy/**`) gained no registry access and no update check; everything below lives in `src/cli/` and runs only when the operator invokes a command. Implementation: `src/cli/registry.ts`, `src/cli/update.ts`; tests: `test/cli/update.test.ts`.

Assets: the bytes every client starts (fixed copies, image IDs), the client configuration files, `setup.json`, the token files (read by the new copy's `--check-config`, never printed or copied), and the operator's trust in "what is installed is what was published".

Actors: a compromised or impersonated registry; an attacker able to publish under the package name; a network adversary between the operator and npmjs.org, ghcr.io or api.github.com; a local same-user process racing the installer; an operator typing the wrong flag; and, in the always-latest mode, the registry at every client start.

A failed rewrite triggers restoration; an interrupted process is recovered before the next mutating update. `setup.json` is written only after all entries move and the journal is committed. Deprecation metadata is separately sanitized and bounded. Release text never supplies the npm version or package bytes. | Compromised release prose may still mislead the operator, but cannot control the installed version. | `release notes strip terminal and bidirectional controls…` |
| TM-U-07 | T,E / Medium | **Local filesystem races.** A same-user process replaces the fixed-copy parent, the temporary directory or a client file with a symbolic link during the update. | Mutating update/rollback processes serialize with an exclusive owner-only lock; fixed-copy enumeration rejects symlink directories, entries and manifests; rollback accepts only canonical fixed-copy paths. Per-client writes remain atomic and static symlinks are refused. Temp npm files are private. | A same-user process can still race path ancestors or other owned client files; the same principal can directly edit those files and token files. Treat that as a same-user residual rather than an isolation boundary. | new writable-state and symlink tests; `a concurrent update is refused…`; prior `npx-install.test.ts` and `uninstall.test.ts` symlink cases |
| TM-U-08 | I / Low | **Update check as an information leak.** `test` and `doctor --online` contact registry.npmjs.org and reveal that this host uses the package. | The check runs only after a successful appliance probe in those two commands, never at server start or from the MCP process. npm children receive only runtime/proxy/CA environment; `.npmrc` data and shell tokens are stripped. `update --check` fetches fixed GitHub release metadata; Docker update additionally contacts GHCR, and pinned update probes the configured appliance. No appliance address, token value or client name is sent to npm, GitHub or GHCR. No telemetry call exists. | The registry sees package/version queries, GitHub sees release/attestation queries, GHCR sees image pulls and the configured appliance receives one signed status request. These are command behavior, not background reporting. | fake registry/GitHub/Docker update tests; existing `test`/`doctor` online tests |

## Decisions

- `update` never runs lifecycle scripts, never follows a configurable registry, never writes a transient `npx` path into a pinned entry, and never prints a token.
- The appliance probe before the rewrite is deliberate even though the previous version already passed it: it catches rotated tokens, changed URLs and expired certificates before a working client is turned into a broken one, at the cost of one signed request.
- The previous copy and image are kept, not deleted, so that `--rollback` works offline; `uninstall` is the single command that removes them, together with everything else the installer created.
- The always-latest mode exists because some operators asked for zero-maintenance clients; it is documented as the unverified path and is never the default.
