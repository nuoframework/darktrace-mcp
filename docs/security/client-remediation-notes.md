# HTTP client remediation notes

## Oracle alignment

- **ST-25.S4:** the previous test plan expected an SDK-style `path?query&{json}` signature and wire query. That oracle conflicts with the live 7.1.0 evidence: the SDK form returned 400, while `path?{json}` returned 200 and the query was excluded from the signature (`docs/security/lab-signing-evidence.md:52-53`, conclusions at `:71-76`). The client now rejects query plus JSON during request construction with `invalid_request`; the S4 KAT was replaced by a zero-signing/zero-network rejection check. If a future route needs S4, only the evidence-backed `path?{json}` signing form can be considered, with the query unsigned.
- **ST-25.S6:** the old KAT expected standard Base64 to be signed and sent raw. Live evidence records raw-signature/wire-encoded as 400 and percent-encoded-as-sent as 200 (`docs/security/lab-signing-evidence.md:45-47`). The updated KAT uses RFC3986 percent encoding for the Base64 path parameter before both signing and transport. The evidence notes that `+` and `/` were inferred from the canonical-equals-wire rule rather than individually probed (`:133-137`); the offline KAT verifies those byte encodings but does not claim another live appliance run.
- **Remaining out-of-scope oracle:** `test/contract/integration.test.ts` still expects the raw S6 wire path and raw-path HMAC. It fails `npm test` for the same evidence conflict above. This file is outside the assigned edit boundary; its test owner needs to update it to the encoded-as-sent vector.
- **Binary output handoff:** `ApiResponse.outputLimitExceeded` is the client-owned, byte-free marker `{errorCode:'output_limit_exceeded', size, sha256}`. The response formatter must return that marker before invoking Base64/file formatting. The current tool formatter does not yet consume it, so the end-to-end `ST-29.ENVELOPE`, `ST-29.OUTPUT`, and `ST-29.ALLOCATION` cases remain failing in that separate layer; the direct client tests confirm no bytes are returned and no oversized Base64 string is allocated.
