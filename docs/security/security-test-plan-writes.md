# Writes & sensitive-read security test plan

**Status: planned acceptance specification; every ST-17–29 case is NOT RUN.** Date: 2026-10-06. Read with the [writes supplement](threat-model-writes.md), historical [ST-01–16](security-test-plan.md), [A1–A8](design-decisions.md) and [MR research](mcp-attack-research.md). This specifies future adversarial tests; it records no source/runtime validation, lab activity or accepted risk. Existing suites and historical evidence remain unchanged.

## Harness and exact observables

Use isolated builds, synthetic tokens/content, a deterministic monotonic clock plus fixed UTC clock, a real child-process stdio harness and transport/signing spies. Deny external DNS/sockets; use loopback TLS only for connector/wire assertions. Observe separate counters for builder entries, signer invocations, DNS resolutions, connection attempts, HTTP requests, elicitation requests and filesystem mutations. A fake operation-client result alone cannot establish zero HMAC or sockets. Instrument the real signer/connector and use process diagnostic guards. Capture stdout, stderr, structured/text results and serialized bytes. Never load deployment credentials.

The following exact contracts are **normative requirements for this supplement**, not assertions that parallel source already exposes these names. A mismatch is a finding requiring owner reconciliation; never change a negative oracle merely to obtain PASS.

* Tool denial is `isError:true`, with `structuredContent.error.code` and `structuredContent.error.message` exactly as below. Its sole text content is the JSON serialization of that same error object (and the correlation/outcome fields specified below), with no raw arguments, exception cause or upstream body. Test codes/messages exactly; generated request IDs are matched by equality across sinks, not fixture literals.
* Unless stated otherwise, a denied call has builder=0, signer=0, DNS=0, connection=0, HTTP=0 and execution audit start/terminal=0. It produces exactly one `error` audit record when the audit sink is healthy. Optional audit failure cannot enable a denied action. Elicitation counts are specified per case. A preview has the same zero effects, elicitation=0 and exactly one `preview` audit record under a healthy sink.
* Ordinary unsigned preview is exactly `{dryRun:true,operationId,method,parameterNames}`. `parameterNames` is the sorted set of validated API parameter names, without control-only fields or values. Critical unsigned preview adds exactly `previewId` (opaque nonempty string) and `expiresAt` (UTC ISO timestamp at creation+300,000 ms). No URLs, canonical signing text, credentials, header values or response data occur. Unknown/malformed input denies instead of generating a preview.
* Bind SHA-256 to UTF-8 canonical JSON `{operationId,args}`: recursively sort object keys by Unicode code point, preserve array order, retain strings without Unicode normalization, normalize valid JSON numbers using JSON serialization, reject nonfinite numbers and ambiguous duplicate keys before parsing/dispatch. `args` contains validated API arguments after deterministic descriptor defaults, excluding only `dryRun`, `confirm`, `previewId`; ordered/repeated query pairs remain ordered arrays. Missing and explicit default are equal only where the reviewed descriptor defines that default. Absent/empty/false/zero/null are otherwise distinct. The SHA-256 digest is lowercase hex; preview ownership also binds session and policy/schema epoch separately.
* Audit JSONL record has exactly `{audit:true,ts,requestId,operationId,outcome,argsHash,approvalMode,seq,prevHash,hash}`. Outcomes are `preview`, `error`, `start`, `ok`, `unknown`; approvalMode is `none`, `elicitation` or `host`. Unknown operation uses fixed `unknown_operation`; invalid/unvalidated args use `argsHash:null`. Otherwise argsHash is the digest above. Seq starts at 1 per process; genesis prevHash is 64 zeroes; hash is lowercase SHA-256 of canonical UTF-8 JSON of all record fields except `hash`. Each subsequent prevHash equals the preceding hash; ts/requestId are generated by code. No additional raw target, payload, bearer previewId or asserted human identity fields. Each completed accepted execution emits exactly one `start` and one terminal `ok`/`error`/`unknown` with shared requestId/argsHash/approvalMode. Preview and execute use distinct requestIds but the same argsHash for the same operation/args. All audit emissions share one serialized chain, including concurrent previews/denials. Diagnostics on stderr are separate fixed non-audit events and must not impersonate audit JSON.

Validation order for deterministic multi-fault cases: lifecycle/input/schema, descriptor/profile/target, dryRun branch, confirm, preview presence/binding/state/expiry, circuit-breaker check, capability/approval capacity, approval, binding/expiry recheck, rate/breaker admission, mandatory audit, builder/sign/HTTP. After reservation, every terminal path consumes the handle. Denials before reservation do not consume it. No policy/schema error may produce a signed request.

## Evidence and gates

Record test/subcase name, TM mapping, source/runtime/harness SHA-256 hashes, frozen manifest/config/budgets, fixture provenance, Node/OS/architecture, command, timestamp, assertion counts and PASS/FAIL/BLOCKED/NOT RUN with sanitized receipt. Run in an isolated fresh build; do not overwrite intermediate failures or auto-refresh snapshots/vectors. A skipped or unimplemented test is not a pass. Documentation cross-checks prove traceability only. Independent reviewers must assess the combined exact snapshot; keep adversarial test ownership separate from source implementation.

The supplied design leaves target/bulk policy, circuit breaker, trustworthy host human approval, combined-profile data flow and upstream idempotency unresolved. ST-17/ST-22/ST-18/ST-23/ST-20 deliberately expose those limits. Ordinary duplicate writes and schema-valid canary copying are expected exposure observations, not grounds to claim those risks closed. Hash-chain verification alone cannot close collector completeness. Offline tests must not be relabeled as appliance ACL, human approval, provider eligibility or SDK/appliance compatibility evidence.

Require two independent design-review rounds, implementation/security evidence, actual package/image byte binding and reviewed tools/list hashes before release. Each increment needs its own manifest and gates. A separately authorized non-production write campaign specifies operation, least-privilege token, sacrificial target, finite calls, undo and cleanup; captures only redacted metadata and audit correlation. Critical RESPOND testing uses only an explicitly authorized synthetic device. No live test, publication or push is authorized by this plan.
