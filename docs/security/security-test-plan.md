# Phase 2 security test plan

**Status: planned; none of the security tests below has been executed.** This is an initial acceptance specification dated 2026-10-05, not a security certification. No live lab or appliance access is part of this task. Read alongside the [threat model](threat-model.md), [architecture](../architecture.md) and [API contract](../api-contract.md).

## Execution strategy

Use TypeScript compiled by `tsc` and the built-in `node:test` runner, as agreed with the coordinator. Test paths below are proposed, not claims that files or runnable commands already exist. Run unit/contract tests with a deterministic clock, seeded jitter, fake credentials, synthetic fixtures, temporary directories and injected transport/DNS/socket abstractions. Add real child-process stdio tests and isolated loopback **TLS** integration tests when the implementation exists. A mocked fetch cannot prove DNS pinning or certificate verification; those assertions require connector-level tests. Ordinary CI must deny external network access for this suite and never load lab credentials. Install/dependency audit jobs use a separate controlled network context.

For negative tests, assert both the error/result and the absence of side effects: zero signer calls where policy denies, zero connection attempts, zero redirected requests, zero writes outside the export directory, or exact retry counts as applicable. Synthetic secret sentinels must be distinctive and include public/private tokens, signature, body content and encoded variants. Capture stdout, stderr, tool content, structured content, error causes, dry-run and audit output. Never store actual keys, PCAP, email or portal source in fixtures.

For every implemented test record: test ID, threat IDs, commit, runtime/OS, sanitized fixture version, configuration and numeric budgets, date, command, pass/fail/blocked/not-run outcome, assertion counts, redacted evidence path and reviewer. A skipped test is not a pass. A documentation cross-reference check only proves traceability, not the effectiveness of controls. Proposed suite locations: `test/security/signer.test.ts`, `network.test.ts`, `policy.test.ts`, `export.test.ts`, `limits.test.ts`, `stdio.test.ts`, with contract fixtures under `test/fixtures/security/`.

## Deferred lab campaign — requires separate authorization

No lab step is authorized by this plan. After architecture and offline gates are reviewed, an operator may authorize a designated 7.1 instance, exact read-only operation list, time window and call/data budget using a least-privilege test token. Start with sanitized version/status checks; settle S1/S6 signing ambiguities using bounded synthetic inputs; collect only redacted request-shape metadata and compatibility results. Do not obtain PCAP/email or mutate appliance state as an incidental authentication test. Query-plus-body, DELETE and email semantics require separately scoped validation if they cannot be resolved safely by read-only work. Never probe arbitrary private addresses or execute attack payloads on production. Writes remain disabled until a distinct action-specific approval; publishing results must not disclose appliance identity, tokens or actual telemetry.

## Open decisions

Track A1–A8 in the threat model, particularly trusted approval, canonicalization modes, optional destination allowlist versus bootstrap-DNS trust acceptance, export quotas/retention and finite concurrency/input/decompression budgets. Reconcile architecture changes before coding; do not weaken a negative test to make an unresolved design pass. Owners of client, policy, exports and release must supply actual evidence before changing any status above.
