# Phase 2 security test plan

**Status: planned acceptance specification; implementation IN PROGRESS, not security validated.** This document records no executed security-test outcomes; implementation workers must attach evidence separately. This is an initial acceptance specification dated 2026-10-05, not a security certification. No live lab or appliance access is part of this task. Read alongside the [threat model](threat-model.md), [architecture](../architecture.md) and [API contract](../api-contract.md).

## Execution strategy

Use TypeScript compiled by `tsc` and the built-in `node:test` runner, as agreed with the coordinator. Test paths below are proposed, not claims that files or runnable commands already exist. Run unit/contract tests with a deterministic clock, seeded jitter, fake credentials, synthetic fixtures, temporary directories and injected transport/DNS/socket abstractions. Add real child-process stdio tests and isolated loopback **TLS** integration tests when the implementation exists. A mocked HTTP method cannot prove DNS pinning or certificate verification; those assertions require connector-level tests. Ordinary CI must deny external network access for this suite and never load lab credentials. Install/dependency audit jobs use a separate controlled network context.

For negative tests, assert both the error/result and the absence of side effects: zero signer calls where policy denies, zero connection attempts, zero redirected requests, zero writes outside the export directory, or exact retry counts as applicable. Synthetic secret sentinels must be distinctive and include public/private tokens, signature, body content and encoded variants. Capture stdout, stderr, tool content, structured content, error causes, dry-run and audit output. Never store actual keys, PCAP, email or portal source in fixtures.

## Deferred lab campaign — requires separate authorization

No lab step is authorized by this plan. After architecture and offline gates are reviewed, an operator may authorize a designated 7.1 instance, exact read-only operation list, time window and call/data budget using a least-privilege test token. Start with sanitized version/status checks; validate eligible S1 signing using bounded synthetic inputs; research on blocked S4/S5/S6 requires separately scoped lab tooling and never enables production shapes; collect only redacted request-shape metadata and compatibility results. Do not obtain PCAP/email or mutate appliance state as an incidental authentication test. Query-plus-body, DELETE and email semantics require separately scoped validation if they cannot be resolved safely by read-only work. Never probe arbitrary private addresses or execute attack payloads on production. Lab writes require distinct action-specific authorization as a procedural requirement; runtime profile configuration does not verify that authorization; publishing results must not disclose appliance identity, tokens or actual telemetry.
